Section 01

Honest Audit — What Exists & What's Broken

Before a single line of new code is written, we need to be completely clear about what Phase 0 delivered, what it did not, and why the system as a whole cannot be used by any real user today.

What Phase 0 Actually Delivered

The backend models for Facility, FacilityService, FacilityInsurer, OpeningHours, Patient, Insurer are correctly designed. The geo-search endpoint GET /facilities/nearby works. The PostGIS GIST index is correctly created. The test suite has 47 backend tests at 87% coverage and 33 frontend tests. The patient PWA renders home screen State A (no active queue) with search and facility cards. The OpenAPI schema is committed. The bundle is 69 KB gzipped, well within the 150 KB budget. This is solid engineering — do not throw it away.

Why No Real User Can Use The System Today

The 25 seed facilities have approximate, unverified coordinates. Distance calculations are wrong. A patient searching for facilities near them gets results that may be kilometres off. The patient app has no Auth (Phase 2), no booking (Phase 2), no queue tracking (Phase 1) — the three things that define the product's value. The provider (reception) app does not exist — meaning no receptionist can enter patients, and therefore the queue data that the patient app would read does not exist. There are no doctor profiles. Walk-in patients have no intake flow. The symptom checker is a placeholder comment. No roles except basic Django admin exist. No one can log in, book, check in, or track a queue.

Section 02

Design System — The Visual Foundation

Every pixel in this system speaks before any word is read. A high-class system is not made of more features — it is made of fewer elements, placed more precisely, with more intention. The design system below is the law. Every component, every screen, every portal inherits from it. Nothing is designed ad hoc.

Design Philosophy

MediLink serves two audiences simultaneously: a rural patient on a low-end Android in a busy waiting room, and a senior doctor or ministry official reviewing analytics on a 27-inch monitor. The design must feel expensive and trustworthy to the official, while remaining crystal-clear and fast to the patient. The answer is precise restraint — not simplicity, not minimalism. Every element is deliberate. No decoration that doesn't carry meaning. Typography does the heavy lifting. White space is generous. Colour is used to communicate state, never for aesthetic variety.

The WebSocket Layer — Why It's Critical

Queue position cannot be polled every 30 seconds in production with 5,000 concurrent users across 100+ facilities. That is 10,000 requests per minute hitting the Django application server. The correct architecture is a WebSocket channel per queue. When a receptionist marks a patient as served, Django Channels broadcasts a queue.update event to all connected clients in that facility's room. The patient app receives it and re-renders the queue card in under 100ms with no polling. Django Channels with Redis as the channel layer is already partially supported by the existing Redis infrastructure.

Walk-in Patients — The Flow That Most Systems Miss

Not every patient books online. At a busy district hospital, the majority arrive at the door without a booking, especially elderly patients and emergency cases. The system must handle this equally well. A walk-in creates a QueueEntry directly through the receptionist's interface — no Appointment record is required. The receptionist can optionally look up a patient by phone number (linking to their profile) or create an anonymous walk-in record with a name only. The walk-in patient gets a printed or displayed ticket code (e.g. A-047). Their position in the queue is determined by joined_at timestamp, same as booked patients. There is no separate queue for walk-ins and booked patients — they share one queue, ordered by arrival time, with urgency overrides available to the nurse.

Doctor Daily Capacity Limit — How It Works

A doctor can set a maximum number of patients per day per service type. This is stored on the ScheduleTemplate model as capacity_per_slot × number_of_slots, and on a new DoctorDailyLimit model for overrides. When the limit is reached, the booking UI marks all remaining slots for that doctor as "Full" and directs the patient to either another doctor at the same facility or a nearby facility. The receptionist also sees a capacity warning when checking in walk-in patients beyond the doctor's daily limit, but can override it with a reason (emergencies, direct referrals). This override is logged.

BackendData

Phase 1 — Reception & Live Queue Engine

Build the provider web app from scratch. This is the phase that makes the product real — live queue data is created here by receptionists, and consumed by patients on their phones.

Next Build Weeks 4–9

Build Order is Non-Negotiable

The patient app queue screen shows live data that only exists when a receptionist has entered it. You cannot build or demo the patient queue screen without the reception app running first and actively managing a queue. Build the provider reception screen first — it is the foundation of the entire product.

P1-01 — Authentication System (Both Apps)

BackendFrontendSecurity

JWT-based authentication for all provider-side users. Patient authentication (OTP) is Phase 2. This phase implements staff login only.

  • Backend: Install djangorestframework-simplejwt. Configure access token lifetime 15 minutes, refresh token 7 days. Store refresh tokens in an httpOnly cookie — never localStorage. Access token sent in Authorization header for all API calls.
  • Endpoints: POST /auth/staff/login (email + password → access + refresh), POST /auth/refresh (refresh → new access), POST /auth/logout (invalidate refresh), GET /auth/me (current user + role + facility).
  • Roles: Implement Django custom permissions: can_manage_queue, can_check_in_patients, can_view_reports, can_manage_facility, can_manage_staff. Every API view checks the exact permission required — never just "is_staff".
  • Facility scoping: Every provider-side queryset is filtered by request.user.staffmember.facility. Implement this as a DRF mixin applied globally to all provider views — not per-view. One line missed means a receptionist can read another facility's patients.
  • Provider login screen: Email + password form. "Forgot password" → email reset link. No registration — accounts created by facility admin or MediLink admin only.

P1-02 — Reception Screen (The Core Screen)

FrontendBackend

Target: complete a patient check-in in under 10 seconds with keyboard only. This screen is the most important screen in the system. Our competitor is a paper register and an overwhelmed receptionist.

  • Layout: Two-panel. Left: check-in form (full width on load). Right: current queue list. On wide screens both panels are visible simultaneously. On a tablet, tabs switch between them.
  • Check-in form — booked patient: Single input field, auto-focused on page load. Accepts phone number or appointment reference code (e.g. ML7K2Q). Press Enter or click Check In. System looks up the matching appointment or walk-in. Displays patient name, insurance, appointment time. One more Enter confirms check-in. Total: 2 keystrokes.
  • Check-in form — walk-in patient: Toggle "Walk-in" mode. Fields: Name (required), Phone (optional — links to patient profile if found), Department (required dropdown), Insurance (optional). Press Enter to add to queue. Total: 4 fields, one Enter.
  • Optimistic UI: The queue list updates immediately when Enter is pressed. The backend confirmation happens in the background. If the backend rejects, show an undo toast. Never make the receptionist wait for a server round-trip.
  • Offline mode: All check-in actions write to IndexedDB first. The queue list is maintained locally. When network returns, sync with POST /queue/sync using the clientRecordedAt timestamp to preserve order fairness. The topbar shows an offline banner with pending action count.
  • Queue list (right panel): Shows all entries for the selected department today. Columns: position number, ticket code, patient name, entry time, wait time, priority badge, status. Action buttons: Call (marks as CALLED), Serve (marks as SERVED), No-show. Emergency/Urgent entries have a coloured left border and appear at the top of their priority lane.
  • Department selector: Prominent tab bar at the top showing all departments the logged-in receptionist manages. Clicking a tab switches both panels to that department's queue.
  • Printed ticket: Each check-in generates a printable ticket with: MediLink logo, facility name, ticket code (A-047), patient name, department, estimated wait, and date/time. Print dialog triggered automatically on check-in or via a manual print button on each row.

P1-03 — WebSocket Queue Engine

BackendInfra

Install Django Channels with Redis channel layer. Every facility-department combination gets its own channel group. When any queue mutation occurs (check-in, serve, call, no-show, priority change), broadcast a queue.update event to all connected clients in that group.

  • Channel naming: queue_{facility_slug}_{service_code} — e.g. queue_chuk_general. All receptionists and patients with active queue entries in that department connect to this channel.
  • Event payload: { type: "queue.update", facility: slug, service: code, entries: [...] } — full queue state, not a delta. Simpler to implement correctly; at 50 patients per queue the payload is negligible.
  • Authentication on WS: JWT token passed as query parameter on WS handshake (ws://...?token=ACCESS_TOKEN). Channels middleware validates the token. Unauthenticated connections are rejected for provider channels. Patient queue channels accept unauthenticated connections for read-only position viewing (ticket code as identifier).
  • Fallback: If WebSocket is not available (corporate proxy, old browser), fall back to 30-second polling on GET /queue/entries/{facility_slug}/{service_code}. The patient app detects WS failure and switches automatically.

P1-04 — Patient App — Home Screen States B & C (Live)

Frontend

These screens only work now that Phase 1 produces live queue data. Implement the live queue card on the patient home screen.

  • State B — in queue: On load, call GET /queue/current. If an active queue entry exists, the search hero is replaced by the QueuePositionDisplay component. The queue number is 72px, white on primary green. Below it: progress bar, ETA, leave-home-by time. Connect to the facility's WebSocket channel. When a queue.update arrives, animate the position number and update ETA.
  • State C — appointment today: If GET /queue/current returns a booked appointment for today but no queue entry yet (patient hasn't checked in), show the appointment card with reference code, time, facility, and directions button.
  • Leave home by calculation: now + eta_minutes - travel_to_facility_minutes - 10_minute_buffer. Travel time from patient's last known location to facility using straight-line distance × 1.3 factor (road correction) ÷ average urban speed 25 km/h. If patient location is not available, hide the line entirely — never fabricate it.
  • Staleness indicator: If the WebSocket is disconnected or the last update was more than 2 minutes ago, show "Updated 4 min ago" in amber text next to the position. A stale number that looks live destroys trust permanently.

P1-05 — Facility Admin Screen (Provider App)

FrontendBackend

The facility admin has higher permissions than the receptionist. Their primary screen is a dashboard showing today's overview across all departments.

  • KPI cards (today): Total appointments, Total check-ins, No-show count, Average wait time, Active queue length across all departments.
  • Department queue overview: One row per department showing: department name, patients waiting, patients seen, current wait estimate, next available slot. Click any row to drill into that department's full queue list.
  • Staff management: Add / remove receptionist accounts. Set role permissions. Reset passwords. View last login time for each staff member.
  • Facility settings: Edit facility profile (name, phone, address, photo). Toggle department availability (temporarily close a department). Manage insurance acceptance.
  • Reports tab: Daily volume chart, average wait time trend (this week vs last week), no-show rate trend. Downloadable as PDF with the facility's name and date range in the header. This is the number that justifies the subscription.

P1-06 — Doctor Schedule Management

FrontendBackend

Doctors manage their own availability. This screen is part of the provider app, accessible only to users with the Doctor role.

  • Weekly availability calendar: A 7-day × facility grid. The doctor checks which days they work at each linked facility and sets start/end time and max patients per day for each slot.
  • Override for specific dates: Mark specific dates as unavailable (holiday, conference). These dates are blocked in the booking calendar for patients.
  • Today's patient list: A simplified list of all queue entries assigned to this doctor today, sortable by queue position. Clicking a patient opens a brief profile card with insurance, triage notes (if recorded by nurse), and last visit summary.

Phase 2 — Booking Engine & Patient Auth

Patients can now create accounts, book appointments with specific doctors, and receive email and push notifications. The online booking flow end to end.

Planned Weeks 10–16

P2-01 — Patient Authentication (Phone + OTP)

BackendFrontendSecurity
  • Flow: Patient enters phone number in E.164 (+250XXXXXXXXX). System generates a 6-digit OTP, valid for 10 minutes, stores as SHA-256(otp + phone + timestamp) in Redis (never in the database). OTP sent via email (if patient has email) or displayed on screen with an instruction to note it (SMS deferred to later phase). Patient enters OTP → system issues JWT access + refresh tokens.
  • Rate limiting: Maximum 5 OTP requests per phone number per hour. Maximum 3 OTP verification attempts before a 30-minute lockout. Store attempt counts in Redis.
  • Anonymous browsing: Search, facility detail, and insurance check all work without auth. Auth is required only at the moment of booking — never before. Respect the design rule: "No login wall."
  • Patient profile screen: Name, language preference, insurance, home location (opt-in), dependent profiles. Privacy section: view consent log, download data, request deletion.

P2-02 — Booking Flow (4-Step Wizard)

FrontendBackend

The 4-step appointment booking flow. Can be entered from a facility card, a facility detail screen, or from the symptom checker result (Phase 4, pre-filled department).

  • Step 1 — Select Department: Show all service types offered by the facility. Each card shows department name, available doctor count, and today's next available slot. If arriving from symptom checker, this step is pre-filled and skipped.
  • Step 2 — Select Date & Time: Calendar strip showing the next 14 days. Grayed dates have no availability. Selecting a date loads available time slots for that day. Slots are shown as a grid (e.g. 8:00, 8:15, 8:30). Full slots are shown struck-through. Partially full slots show remaining capacity (e.g. "2 left"). Slots refresh every 30 seconds to prevent double-booking UI issues.
  • Step 3 — Select Doctor: List of doctors available on the selected date and time at this facility in the selected department. Each card shows: name, photo, specialisation, years of experience, insurances accepted, and average consultation duration. Patient can select any available doctor or "Any available doctor" to let the system assign.
  • Step 4 — Confirm: Summary card showing: facility, department, date/time, doctor, insurance match, appointment reference code. A clear disclosure: "By booking you confirm you will cancel at least 2 hours in advance if you cannot attend." Tap Confirm → appointment created → confirmation screen with QR code → push notification permission request.
  • Double-booking prevention: A UniqueConstraint on (patient, facility, slot_start) with status in (booked, arrived) prevents the same patient from double-booking. The frontend also checks on Step 2 selection, but the database constraint is the authoritative guard.
  • Doctor daily capacity enforcement: When generating available slots, the backend checks DoctorAvailability.max_patients_per_day against already-booked appointments. If the doctor is full for the day, their name does not appear on Step 3. The receptionist can override this for walk-ins but the system logs the override.

P2-03 — Notifications (Email & Web Push)

BackendInfra
  • Booking confirmation: Sent immediately via email (if available). Contains: reference code, facility, date/time, doctor name, how to cancel.
  • Appointment reminder: Celery beat task sends 24 hours before and 2 hours before. Via push notification (if granted) and email.
  • Queue position updates: Web push notification when patient's position drops to ≤3 ahead. Message: "You are almost up — make your way to {Facility Name} now."
  • Cancellation: When a facility cancels an appointment (doctor unavailable, facility closed), all affected patients receive immediate notification with a rebooking deep-link.
  • No-show follow-up: 30 minutes after a missed appointment, send a push/email: "Did you miss your appointment at {Facility}? You can rebook here." This is a courtesy, not a penalty.
  • Duplicate prevention: The UniqueConstraint on (queue_entry, kind) in the Notification model prevents the same alert from being sent twice. Celery tasks must check before sending.

P2-04 — My Bookings & Visit History Screens

Frontend
  • My Bookings screen: Two tabs — Upcoming and Past. Upcoming shows all booked appointments in chronological order with status badges (Booked, Checked In, In Progress). Past shows completed visits with date, facility, doctor, and a "Book again" shortcut.
  • Appointment detail: Full detail screen for each booking. Shows QR code (scannable by receptionist as alternative to code entry), directions button, cancel button (disabled if less than 2 hours away).
  • Cancel flow: Tap cancel → confirmation dialog with reason selector (can't make it / feeling better / found another facility / other). Confirmation is required — no accidental cancellations. On cancel, slot is freed immediately and a cancellation confirmation is sent.

Phase 3 — Clinical Interface

The doctor's workstation and the nurse's triage panel. This is where patient care happens. Speed, clarity, and clinical information hierarchy are everything.

Planned Weeks 17–22

P3-01 — Nurse Triage Panel

FrontendBackend

The nurse sees the queue list and can record vitals for each patient before the doctor sees them. This screen is optimised for speed — a nurse may triage 30 patients in a morning.

  • Queue list with triage status: Each queue entry shows a colour-coded triage status indicator — green dot (triaged), orange dot (waiting for triage), red dot (urgent flag). The nurse works through untriaged patients in order.

All fields optional — the nurse records only what is available. One-click save. The form pre-fills from the patient's last visit if they have been before.
  • Priority escalation: A large "Mark Urgent" button at the top of the triage form. Requires a brief reason (dropdown: deteriorating vitals / patient distress / clinical judgement / other). When marked urgent, the queue entry moves to the Urgent lane and a real-time alert appears on the receptionist and doctor screens.
  • Emergency escalation: A separate "Emergency" button (red, prominent). Triggers the Emergency protocol: queue entry status set to Emergency, receptionist notified immediately, entry moves to the top of all lanes, an optional note to call for doctor assistance.

P3-02 — Doctor Workstation

FrontendBackend

The doctor's primary screen during clinic hours. Split-panel: patient list on the left, patient detail on the right. Speed is the design constraint — the doctor spends at most 5 seconds reading the left panel before calling the next patient.

  • Patient list: Ordered by priority lane (Emergency → Urgent → Routine), then by queue position within each lane. Each row shows: position, patient name, age if available, insurance badge, triage status indicator, time waiting. Urgent and Emergency rows have coloured left borders (amber and red respectively).
  • Current patient banner: A prominent banner at the top of the right panel shows the currently active patient — the one the doctor is seeing now. Large name, insurance, time started.
  • Patient detail — right panel: Seven information blocks in a fixed layout. (1) Patient demographics: name, age, phone, insurance. (2) AI symptom summary if the patient used the symptom checker (Phase 4 — shown as a read-only card). (3) Triage vitals recorded by nurse — shown as a compact grid. (4) Visit history — last 3 visits at any facility, condensed to date + diagnosis. (5) Notes and prescription — the doctor types here. Auto-saves every 10 seconds. (6) Referral — optional, opens a facility search to select where to refer to. (7) Actions — Mark Seen, Mark No-show, Refer.
  • Notes auto-save: The prescription / notes textarea auto-saves to PATCH /triage/visit-notes/{id}/ every 10 seconds. A subtle "Saved" indicator appears. Draft is preserved even if the doctor accidentally closes the tab.
  • Mark Seen: Closes the visit. The queue entry moves to SERVED status. The next patient in the queue is automatically highlighted. The doctor's daily patient count increments.

P3-03 — Referral System

BackendFrontend
  • Doctor initiates referral: On the patient detail panel, tapping Refer opens a facility search filtered to the required specialty and the patient's insurance. The doctor selects a facility and optionally writes a referral note.
  • Referral record: A Referral record is created linking the current visit note to the target facility. The patient receives a notification with the referral details and a direct booking link to the target facility pre-filled with the appropriate department.

Phase 4 — AI Symptom Checker

The symptom checker that routes patients to the right specialist before they travel. Not a diagnosis tool — a routing tool. The distinction is non-negotiable.

Planned Weeks 23–30

P4-01 — Symptom Checker UI

Frontend
  • Entry point: The symptom checker is NOT a primary button on the home screen. It is accessed from "Not sure which doctor?" link inside the search flow, and from the Quick Actions grid as a secondary option. This is intentional — prominence invites self-diagnosis rather than care-seeking, which is both a clinical risk and a liability.
  • Conversational UI: A guided chat-style flow. The AI asks structured questions one at a time. The patient can select from symptom chips or type in free text. Multilingual — all prompts and responses in the patient's selected language (RW/EN/FR).
  • Symptom input: Multi-select from a curated list of common symptoms relevant to Rwanda's disease burden (malaria, typhoid, TB, respiratory infections, hypertension, maternal symptoms, paediatric conditions). Free-text fallback for symptoms not in the list. Duration selector (1 day, 2–3 days, 1 week, 2+ weeks). Severity selector (Mild / Moderate / Severe).
  • Result display: Ranked probability list (top 3 conditions, confidence percentage for each). Recommended specialist type. Disclaimer — always visible, never collapsible: "This is a guide to help you find the right care — it is not a medical diagnosis. Always consult a doctor."
  • Emergency detection: Specific symptom combinations trigger immediate emergency display: chest pain + shortness of breath, loss of consciousness, severe bleeding, stroke symptoms (face drooping, arm weakness, speech difficulty), seizures, high fever in infant. When detected, the booking flow is completely bypassed. A full-screen red alert shows: "These symptoms may be an emergency. Go to the nearest Emergency Department immediately or call 912." A map showing nearest A&E facilities is displayed below.
  • Booking integration: Below the result, a "Find a [Specialist type] near me" button triggers a facility search pre-filtered to that specialist and the patient's insurance. One tap from result to booking Step 1.

P4-02 — ML Inference Service

BackendInfra

A separate Python FastAPI microservice that receives symptoms and returns a ranked list of likely conditions with confidence scores. Runs independently from the Django app — can be retrained and redeployed without touching the booking system.

  • Model: Phase 4 uses a fine-tuned text classification model trained on symptom-disease data specific to Rwanda's common disease burden. Initial training data: WHO AFRO disease burden statistics, Rwanda HMIS data (if accessible), and curated symptom-disease mappings from Rwandan clinical guidelines.
  • Input: { symptoms: ["fever", "headache", "joint_pain"], duration_days: 3, severity: "moderate", patient_age_group: "adult" }
  • Output: { conditions: [{ name: "Malaria", confidence: 0.74, specialist: "general_practitioner" }, ...], emergency_flags: [], disclaimer: "..." }
  • Minimum confidence threshold: If no condition exceeds 40% confidence, default to recommending General Practitioner. Never display a result that sounds like a diagnosis when confidence is low.
  • Emergency flag rules: Hard-coded rule engine (not ML) that runs before the ML model. If any emergency symptom combination is detected, return emergency_flags: ["chest_pain_dyspnea"] regardless of ML output. Hard-coded rules are auditable and never drift.
  • Accuracy monitoring: Log all symptom inputs and outputs (with patient consent). Build a feedback loop: when a doctor records a confirmed diagnosis in VisitNote and the patient had used the symptom checker before booking, compare the AI prediction to the confirmed diagnosis. Report accuracy monthly. Retrain when accuracy drops below 65%.

Section 12

Security Architecture

Security in a healthcare platform is not optional and it is not a phase — it is built in from the first line of code. The following requirements apply from Phase 1 onwards. Everything involving patient health data is subject to Rwanda Law No. 058/2021 on the Protection of Personal Data and Privacy.

Authentication & Session Security

🔐
JWT with Short-Lived Access Tokens
Access tokens expire in 15 minutes. Refresh tokens expire in 7 days, stored in httpOnly cookies — never localStorage. httpOnly prevents JavaScript access, eliminating XSS token theft entirely. Refresh token rotation on every use — old refresh tokens are invalidated immediately after issuing a new one. If a token is used twice (replay attack), both the old and new tokens are invalidated and the user is logged out.
🔒
Refresh Token Blacklist in Redis
On logout, the refresh token JTI (JWT ID) is added to a Redis blacklist with a TTL equal to the token's remaining validity. Every token refresh checks against this blacklist before issuing a new token. This is the mechanism that makes logout actually work with JWT — without it, a stolen refresh token is valid until natural expiry.
📱
OTP Security
OTPs are stored as SHA-256(otp + phone + timestamp_minute) in Redis, never in the database. This means even if Redis is compromised, the OTPs cannot be reversed without knowing the timestamp and phone. Maximum 5 OTP send requests per phone per hour. Maximum 3 verification attempts per OTP before a 30-minute lockout. After lockout, the next OTP request resets the counter. All OTP events (request, success, failure, lockout) are logged.
🏥
Role-Based Access Control (RBAC)
Six roles in the system: Patient, Receptionist, Nurse, Doctor, Facility Admin, MediLink Admin, MoH Officer. Each has an exact permission set. No role inherits from another — permissions are explicit. Every API view has a DRF permission class that checks the exact permission. Facility-scoped roles (Receptionist, Nurse, Doctor, Facility Admin) have every queryset filtered by their facility — a nurse at CHUK cannot see a single queue entry from King Faisal Hospital, even if they know the ID.

Data Security & PDPL Compliance

🔒
Encryption at Rest and in Transit
All data encrypted at rest using PostgreSQL's filesystem-level encryption (pgcrypto) and cloud provider disk encryption. All data in transit over TLS 1.3 minimum. HTTP Strict Transport Security (HSTS) headers on all domains. TLS certificates from Let's Encrypt, auto-renewed. No TLS 1.0 or 1.1 — blocked at the load balancer level.
🇷🇼
PDPL Compliance (Law 058/2021)
Rwanda Law No. 058/2021 requires explicit, informed, specific consent before processing personal health data. Every patient must grant a ConsentRecord for (1) data storage, (2) symptom checker AI processing, and (3) sharing visit notes with doctors. Consent can be revoked at any time from the patient profile. Revoking data_storage consent triggers the deletion request flow. No health data is processed without a valid ConsentRecord. This check is enforced at the service layer, not just the view layer.
🗑️
Right to Erasure Implementation
When a patient requests deletion: (1) Patient record is soft-deleted immediately — removed from all search results. (2) A DeletionRequest record is created with a 7-day window. (3) On day 7, a Celery task executes hard deletion: Patient row deleted, all QueueEntry and Appointment records anonymised (patient FK set to null, walk_in_name set to "DELETED"), VisitNote content redacted, ConsentRecord marked deleted. (4) AuditLog entries are retained permanently — they are legally required records and cannot be deleted even on erasure request. The phone number is hashed in the audit log after deletion so the audit trail is preserved without identifying the individual.
📋
Audit Log — Append-Only
The AuditLog table has no UPDATE or DELETE permissions for any database user, including the Django application user. This is enforced at the PostgreSQL role level — a REVOKE statement removes UPDATE and DELETE on the audit_auditlog table from the app database role. Even if the application is fully compromised, the audit log cannot be modified. All sensitive actions are logged: patient data access, role changes, privilege escalation, failed authentication attempts, data export, deletion requests.
🩺
Visit Note Access Controls
A VisitNote can only be read by: (1) the doctor who wrote it, (2) any doctor at the same facility who is actively treating the patient (i.e. the patient has an active queue entry at that facility on that day), (3) the patient themselves if they have consented to view their records. No other staff member can read visit notes — not the receptionist, not the facility admin, not MediLink admin. This is enforced in DRF permissions, not just the frontend.

Network & Infrastructure Security

🛡️
Rate Limiting on All Public Endpoints
All public endpoints rate-limited using Django REST framework's throttling. Authenticated endpoints: 1000 requests/hour per user. Anonymous endpoints (facility search): 100 requests/hour per IP. Auth endpoints (OTP request): 5 requests/hour per phone, 10 per IP. Throttle state stored in Redis. On throttle trigger: return 429 with Retry-After header.
🌐
CSRF Protection
Django's CSRF protection enabled for all session-based endpoints. For the SPA frontend using JWT in Authorization headers (not cookies), CSRF is not applicable to those endpoints. However, the refresh token is in an httpOnly cookie, which requires CSRF protection on the /auth/refresh endpoint. Implement the SameSite=Strict cookie attribute as the primary CSRF defence, with Django's CSRF middleware as the secondary defence.
🔍
Security Headers
All responses must include: Content-Security-Policy (strict — only allow scripts from own domain and Google Fonts for the font CDN), X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, Permissions-Policy: camera=(), microphone=(), geolocation=(self). Use django-csp for automatic CSP header generation. Test with Mozilla Observatory — target grade A+.
🗄️
Database Security
Separate PostgreSQL roles: medilink_app (read/write on application tables, no UPDATE/DELETE on audit_auditlog), medilink_read (read-only, for reporting queries), medilink_admin (DDL, for migrations — never used by the running application). No application query uses raw SQL — DRF querysets and Django ORM only. All user-supplied values passed as parameterised queries — SQL injection is architecturally impossible through the ORM. National ID stored as SHA-256 hash with server-side pepper (stored in environment, never in the database or code).

Frontend Security

⚠️
XSS Prevention
React's JSX automatically escapes all values interpolated into JSX — this is the primary XSS defence. Never use dangerouslySetInnerHTML unless rendering content that has been server-side sanitised with bleach (doctor notes rendered to patient in Phase 3). No eval(), no dynamic script injection. All external URLs (facility map links, directions) opened via window.open with rel="noopener noreferrer". Content Security Policy headers block inline scripts and eval at the browser level.
📦
Dependency Security
Run npm audit and pip-audit in CI on every pull request. Block merges if critical vulnerabilities exist. Use Dependabot for automated dependency update PRs. Pin all major dependency versions — avoid open version ranges like "^4.x" for security-sensitive packages. Audit the full dependency tree quarterly.
🔑
Secrets Management
No secrets in code or in the git repository. Django SECRET_KEY, database credentials, JWT signing key, VAPID keys, SendGrid API key, and all third-party credentials stored as environment variables injected at runtime. Use Docker secrets or cloud provider secret manager (AWS Secrets Manager / Google Secret Manager) in production. Rotate all secrets on a 90-day cycle. If a secret is accidentally committed, rotate it immediately — treat it as compromised regardless of whether it was accessed.
