Reception Check-In Component — Full Specification

Frontend · web-providerBackendWebSocket

This is the most operationally critical component in the system. Every decision in its design is made with one constraint: a receptionist working under pressure, possibly on a cheap shared monitor, possibly with a line of patients at the door, must be able to check in a patient in under 10 seconds using only the keyboard.

  • Initial render: The phone/code input field receives focus automatically on page mount and on every successful check-in. The cursor is always in the input. The receptionist never reaches for the mouse during normal operation.
  • Input handling — booked patient: Input accepts phone numbers in any format (078XXXXXXX, +25078XXXXXXX, 078 XXX XXXX) and appointment reference codes (ML7K2Q). On Enter or button click, the system normalises the input to E.164 and calls GET /patients/{phone} or GET /scheduling/appointments?reference={code}. Response time target: under 300ms (cached patient lookups via Redis).
  • Lookup result display: If a match is found, a confirmation card slides down below the input field showing: patient name, insurance badge, appointment time and department, "arrived on time" or "X minutes late" indicator. The receptionist presses Enter again (or clicks Confirm) to complete check-in. The card has a 500ms appear animation — fast enough to not feel slow, deliberate enough to be readable.
  • Walk-in mode toggle: A clearly visible "Walk-in" toggle button adjacent to the input. When activated, the form expands to show: Name (required), Phone (optional — system attempts to link to existing Patient record), Department (required — dropdown of all open departments today), Insurance (optional). Each field has a keyboard shortcut label shown next to it. Tab advances between fields.
  • Optimistic UI contract: The moment the receptionist presses Confirm (Enter or button), the new queue entry appears at the bottom of the queue list immediately. The entry shows a "Syncing…" indicator. The backend call is fired in the background. If the backend returns success, the "Syncing…" indicator is replaced with the server-assigned ticket code. If the backend returns an error, the entry is removed with a toast notification: "Check-in failed — [reason]. Tap to retry." The entry can be retried from the toast, not by re-entering the information.
  • Offline mode contract: If the network is unavailable, the form continues to accept check-ins. Each pending check-in is stored in IndexedDB as a PendingAction with a locally generated UUID (the Idempotency-Key) and a clientRecordedAt timestamp. The topbar shows "Offline — 3 pending". When the network returns, a background sync posts all pending actions to POST /queue/sync. The sync endpoint is idempotent on the UUID — if any action was already processed (from a previous partial sync), it is skipped, not duplicated. The queue list is maintained from IndexedDB while offline and reconciled with the server response on sync.
  • Printed ticket trigger: After every successful check-in (online or offline-pending), a browser print dialog opens automatically if the facility has "auto-print tickets" enabled (configurable in Facility Settings). The print template is a compact card: MediLink logo, facility name, date, ticket code in large bold type, patient name, department, estimated wait time (if available). The print dialog can be suppressed by the receptionist holding Shift while pressing Enter on the confirmation.
  • Department tab bar: The entire reception screen is scoped to one department at a time. The tab bar at the top shows all departments the logged-in receptionist has access to. Clicking a tab switches both the check-in form context (walk-in department pre-selects to the active tab's department) and the queue list. Tab badge shows current waiting count per department.

The Keyboard Shortcut Map

  • Alt+W — toggle Walk-in mode
  • Alt+1 through Alt+5 — switch department tabs
  • Enter — submit the currently focused action (check-in, confirm, retry)
  • Escape — cancel current action, return focus to input field
  • Tab — advance through walk-in form fields
  • These shortcuts must not conflict with browser or OS defaults. Test on Chrome, Firefox, Edge on both Windows and Ubuntu.

QueuePositionDisplay — Full Specification

Frontend · web-patientWebSocket

The single most visible element the patient ever sees. This component must work in direct sunlight, on a low-end Android screen with reduced brightness, at arm's length. Every design decision serves legibility and trust.

  • Position number: Font size 72px on mobile, 96px on tablet. Font weight 900. White text on primary green background. The number must fill most of the card's vertical space. A patient in a moving vehicle glancing at their phone must be able to read it.
  • Animation on update: When position changes, the number scales from 1.0 → 1.08 → 1.0 over 300ms with an ease-out curve. The background briefly brightens (opacity overlay from 0 → 0.15 → 0 over 400ms) to signal the update. No jarring flashes — this is a healthcare app, not a game.
  • Progress bar: A horizontal bar below the number showing: filled (success green) = patients already seen today, amber segment = the current patient's position, grey = patients still waiting. The bar should be 10px tall, full width of the card. Each segment's width is proportional to its count. Label: "3 seen · You (#4) · 44 waiting".
  • ETA display: "About 28 minutes" — never "28 minutes" (the word "About" signals we know this is an estimate). Font size 18px, weight 600, below the progress bar. If ETA is null (facility not reporting or sample size too low), show "Wait time not available" in muted grey — never hide this section, never show a fabricated number.
  • Leave home by: "Leave home by 10:15" — font size 16px, weight 700, amber colour to draw the eye. Hidden entirely if patient location is unknown (never fabricate it). The calculation: currentTime + etaMinutes - travelMinutes - 10. Travel minutes calculated from patient home location to facility using straight-line distance × 1.3 correction factor ÷ 25 km/h urban speed. Round up to nearest 5 minutes — always conservative.
  • Staleness indicator: Below the ETA: "Updated 2 min ago" in small grey text. If the WebSocket is disconnected, replace with "Connection lost — refreshing…" in amber and attempt reconnect. If last update was more than 5 minutes ago while supposedly connected, show "Data may be outdated" warning. Trust is the product — a stale number that looks fresh is worse than no number.
  • Doctor assigned panel: A secondary card below the main card showing the assigned doctor's name and initials avatar. Appears once a doctor has been assigned at check-in. Hidden if no doctor assigned yet.
  • Action buttons: Two buttons at the bottom: "Get directions" (opens maps app with facility coordinates) and "Cancel appointment" (destructive — shows confirmation modal with reason selector before executing).

Booking Wizard — Step-by-Step Specification

Frontend · web-patientBackend

The booking flow is a 4-step wizard. State is held in a React context that persists across steps. If the user navigates back, their selections are preserved. If they close the app and return on the same day, the context is restored from sessionStorage.

  • Step 1 — Department: A grid of service type cards. Each card: icon, department name in all three languages (RW default), number of available doctors today, earliest available appointment time. Cards with no available doctors are shown last, visually dimmed, with "No availability today — see tomorrow" label. Clicking a card advances to Step 2.
  • Step 2 — Date & Time: A horizontal calendar strip showing 14 days. Dates with no availability are shown grey and unclickable. Selecting a date triggers GET /scheduling/slots?facility={slug}&service={code}&date={date}. Slots render as a 3-column grid. Each slot: time, capacity indicator (e.g. "2 left" when partially full, struck-through when full). Slots refresh every 30 seconds — a subtle "Refreshing…" indicator on the slot grid, not a full page reload.
  • Step 3 — Doctor: Doctors available for the selected slot, filtered by the patient's registered insurance. Each doctor card: 48px circular photo (initial avatar fallback), name, specialisation, years of experience, languages spoken, insurances accepted, average consultation duration. A "Any available doctor" card appears first — selecting it assigns the doctor at check-in time. Clicking a specific doctor card selects them. Selected card shows primary green border and check icon.
  • Step 4 — Confirm: A summary card with all selections. An editable section — clicking any field takes the user back to that step. Insurance match confirmation: green chip "Your Mutuelle is accepted here". Consent disclosure: one sentence in plain language. Confirm button: large, full-width, primary green, "Confirm appointment". On tap, the button enters loading state (spinner, locked width). On success, navigate to Confirmation screen with a smooth slide transition.
  • Confirmation screen: "Appointment confirmed" heading. Reference code in large monospace font (e.g. ML7K2Q) with a "Copy" button. QR code below (encodes the reference code — scannable by receptionist at check-in). "Add to calendar" button (generates .ics file). Push notification permission prompt (only if not already granted). "Done" button navigates to home screen State C.
  • Error handling: If a slot becomes unavailable between Step 2 selection and Step 4 confirmation (race condition), the backend returns 409. The wizard returns to Step 2 with a toast: "That slot was just taken — please choose another time." The slot grid refreshes to show the updated availability.

Doctor Workstation — Interaction Specification

Frontend · web-providerBackendWebSocket
  • Auto-advance on serve: When the doctor clicks "Mark Seen", three things happen simultaneously: (1) the current patient's queue entry transitions to SERVED, (2) the next patient in the priority-sorted queue is automatically highlighted in the left panel, (3) the right panel transitions to show the next patient's information. The transition is a horizontal slide (250ms ease) — the detail panel slides out left, new patient slides in from right. This makes the rhythm of a busy clinic session feel smooth rather than jarring.
  • Visit note auto-save: The prescription/diagnosis textarea fires a PATCH /triage/visit-notes/{id}/ call every 10 seconds if the content has changed since the last save. The call uses a debounce — if the doctor is actively typing, the save is deferred until 3 seconds of inactivity, then fires. A subtle "Saved ✓" indicator appears for 2 seconds in the top-right of the notes panel after each successful save. If the save fails (network error), the indicator shows "Save failed — retrying" in amber. The local draft is preserved in memory until the next successful save.
  • Symptom checker integration: If the patient used the symptom checker before booking, their session is attached to the queue entry. In the patient detail panel, a collapsible card shows: "Patient-reported symptoms: Fever, Headache (3 days, Moderate) · AI suggestion: Malaria (74%)". This is a read-only informational card — it never changes the doctor's workflow, only informs it. The disclaimer "This is AI-generated guidance only" appears below.
  • Three-lane queue rendering: Emergency entries appear at the top of the list with a red left border and "EMERGENCY" pill badge. Urgent entries appear next with an amber left border and "URGENT" badge. Routine entries follow. Within each lane, ordering is by joined_at ascending (arrival time). The doctor can filter to show only one lane. Lane counts are shown in the header: "Emergency (0) · Urgent (2) · Routine (18)".
  • Patient history truncation: Visit history shows the last 3 visits at any MediLink-connected facility. Each visit shows: date, facility name, diagnosis (from VisitNote, if the patient has consented to share). If the patient has not consented, the field shows "Patient has not shared visit history". This consent check is enforced at the API level — the endpoint returns a masked response, not the application deciding to hide it.

Field Testing Protocol

Testing

Before each phase goes live, conduct a structured field test with real users in the target environment. Lab testing cannot replicate the conditions of a busy Kigali health centre.

  • Phase 0 field test: Give 10 people (mixed ages, mixed tech comfort) a phone loaded with the patient app. Ask them to find a facility near them that accepts Mutuelle. Observe without helping. Record every moment of confusion. Fix every friction point before Phase 1.
  • Phase 1 field test: Recruit a receptionist from a willing health centre. Give them the reception app on a tablet. Ask them to process 20 patient check-ins. Time each one. Target: under 10 seconds from the 5th check-in onwards (after initial familiarity). Record every moment of confusion.

Deployment Architecture

The deployment architecture evolves across phases. Start simple — one server can handle the entire Phase 0–2 load. Scale at Phase 3 when you have real users to justify the infrastructure cost.

Phase 0–2 Deployment — Single Server (Sufficient)

Infrastructure

A single Ubuntu 24 VPS with 4 vCPUs and 8 GB RAM can comfortably handle 50 concurrent users and 20 active facilities. This is the right starting point — do not over-engineer the infrastructure before you have the user load to justify it.

CI/CD: GitHub Actions builds Docker images on merge to main, pushes to GitHub Container Registry, Watchtower pulls and restarts
  • TLS: Let's Encrypt via Certbot. Auto-renewal via systemd timer. HSTS header set from day one.
  • Database backups: pg_dump to S3-compatible storage (MinIO or AWS S3) every 6 hours. Backup retention: 30 days. Test restore quarterly.
  • Static and media files: Served via Nginx. Patient app build artifacts are static files. Doctor photos and facility images stored on S3.
  • Environment variables: Stored as Docker secrets. Never in the compose file itself. A .env.production file is gitignored and manually placed on the server.
  • Monitoring: Uptime Robot for external ping (free tier). Django logging to structured JSON → collected by a log shipping agent → stored in a centralised log viewer (Grafana Loki or Papertrail).

Phase 3–5 Deployment — Scale When Needed

Infrastructure

When active facilities exceed 50 or concurrent users exceed 200, the single-server architecture starts showing strain — primarily on the WebSocket layer (Daphne does not scale horizontally without a load balancer aware of sticky sessions) and the PostgreSQL query load. Migrate at this point, not before.

  • WebSocket scaling: Move to a managed Kubernetes cluster (e.g. Google GKE or AWS EKS). Run multiple Daphne pods behind a load balancer with sticky sessions. Redis channel layer already handles cross-pod event propagation — the architecture is ready, only the container orchestration changes.
  • Database read replicas: The reporting queries (facility reports, national MoH dashboard) can be expensive. Add a read replica for reporting endpoints. Route all read-heavy queries to the replica. Django supports multiple databases natively.
  • CDN for patient app: Serve the web-patient build from Cloudflare or AWS CloudFront. The PWA's static assets (JS, CSS, icons, fonts) are cached at the CDN edge. Reduces first load time for patients across Rwanda significantly — the CDN point of presence in Nairobi is far faster than a VPS in Frankfurt.
  • ML inference service: Phase 4's FastAPI inference service runs as a separate container from day one. In Phase 3–5, scale it independently — it has no database and can run multiple instances behind a load balancer trivially. If inference latency becomes an issue, migrate to a GPU instance for this service only.

  • Branch protection: The main branch requires all CI checks to pass before merge. No force pushes. No self-merge without a reviewer approval.
  • Staging environment: From Phase 2 onwards, run a separate staging environment pointed at a staging database with anonymised seed data. Every PR is deployed to staging automatically. The staging URL is shared with testers and partners.
  • Database migrations in CI: Migrations run automatically as part of the deploy step. Migrations that could cause table locks (e.g. adding a non-nullable column to a large table) are written as two-migration sequences — first add nullable, second add the constraint — to avoid downtime.

The Milestone That Changes Everything

The moment that changes the trajectory of this project is not a launch date or a feature flag — it is the first time a real receptionist at a real health centre types a patient's phone number into the reception app, presses Enter, and the patient's phone updates their queue position in real time. That moment makes the product real. Everything in this roadmap is pointing at that moment. Every decision, every component specification, every test case. Get there as fast as possible with as much quality as the timeline allows. That is the mission.

Section 19

Open Questions — Decisions Required

These are not design decisions made in this document — they require input from stakeholders, clinical advisors, or external partners. They must be resolved before the adjacent phase begins.

Must Decide — Phase 1
Who creates facility admin accounts?
When a new facility is onboarded, a MediLink admin creates their first admin account and emails them credentials. Or does the facility self-register? If self-register, how is the facility identity verified before the account is active? A compromised onboarding flow puts fake facilities in the directory. Recommendation: MediLink admin creates accounts manually for Phase 0–1, automate with verification in Phase 5.
Must Decide — Phase 1
Which email service provider for OTP and notifications?
SendGrid and AWS SES are the two viable options. SendGrid has better deliverability and a generous free tier. SES is cheaper at scale. Rwanda email deliverability from international providers can be inconsistent — test both before committing. Decision needed before Phase 2 notifications are built.
Must Decide — Phase 1
Rwanda server location — data residency
PDPL Law 058/2021 has data residency implications for health data. Does MediLink need to store patient data in Rwanda? Closest major cloud regions: Johannesburg (AWS af-south-1), Nairobi (Google africa-northeast1 in preview). A VPS provider in Rwanda (if available) may be required for compliance. Legal advice needed before Phase 1 deployment.
Must Decide — Phase 2
Subscription pricing and payment method
The business model is facility subscriptions. What are the plan tiers? What is the price for a health centre vs a district hospital? MTN MoMo is the obvious payment method for Rwanda — does MTN's API support recurring subscriptions or only one-time payments? If only one-time, is renewal manual (invoice) or automated? Decision needed before Phase 2 subscription management is built.
Must Decide — Phase 2
Walk-in patients without phones — privacy and record-keeping
When a receptionist adds a walk-in with name only (no phone), that patient has no account and cannot track their queue. Their record is anonymous. Should anonymous queue entries be deleted at end of day, or retained for operational statistics? If retained, for how long? This is a PDPL question — retaining anonymous health service records (even without a name) has compliance implications.
Must Decide — Phase 4
Training data source for the ML symptom checker
The ML model needs training data specific to Rwanda's disease burden. Possible sources: WHO AFRO regional disease burden statistics (public), Rwanda HMIS data (requires MoH partnership), retrospective diagnosis data from pilot facilities (requires patient consent and ethics review), open-source symptom-disease datasets from similar sub-Saharan African contexts. At least one of these must be secured before Phase 4 begins. An ethics review may be required depending on data source.
Must Decide — Phase 5
MoH partnership and data sharing agreement
The MoH dashboard requires a formal data sharing agreement between MediLink and the Ministry of Health. What aggregate statistics can be shared? Who owns the data? What are the terms of the partnership? This is a legal and policy question, not a technical one — but it gates Phase 5.
The Core Promise
"You are number 8. Leave home by 10:15."
Every line of code in this system exists to produce that sentence, and to deliver it to a patient reliably, honestly, and with enough design quality that they trust it. That trust is earned one verified facility coordinate at a time, one honest wait estimate at a time, one receptionist who can actually check in a patient in under 10 seconds.
